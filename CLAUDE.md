## Security model (do not weaken)

- Real boundary = Supabase **RLS + `SECURITY DEFINER` RPCs**. Client code is not a security layer — the browser holds the publishable anon key + the user's own JWT, so it can call Supabase directly (bypassing the Next.js server and every Server Action guard) via browser devtools. **`requireAdmin()` checks in Server Actions are defense-in-depth, not the boundary — RLS is.**
- Only `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` (publishable) reach the browser. **Never** put the service_role key client-side.
- Money (net revenue, VAT, expense totals, payslip figures) is **recomputed server-side** (Server Actions / `lib/payslip.js` `computePayslip()`) — never trust client-sent totals.
- Auth: login is a Server Action (also checks `profiles.is_active`); `middleware.js` guards every route; pages use `requireSession()` (`lib/session.js`, also re-checks `is_active` and signs out disabled accounts).
- **`lib/perms.js` is a UI + Server Action gate, not the data boundary.** It hides nav tabs *and* create/edit/delete controls, and `requireCap()` in Server Actions rejects writes that exceed the configured level. **RLS is still the real boundary** — the matrix can only further restrict, never grant more than RLS allows (e.g. staff still cannot DELETE sales even if set to แก้ได้).
- Levels per page (hierarchical): **ซ่อน < ดูอย่างเดียว < กรอกอย่างเดียว < แก้ได้**. Stored in `business_config.role_perms` as `{ role: { '/href': 'none'|'view'|'create'|'edit' } }`. Old boolean `true`/`false` still loads (staff `true` → กรอกอย่างเดียว, manager+ `true` → แก้ได้). Admin is always full. `loyalty_staff` can only be configured on `/loyalty`. Settings UI (`app/settings/role-perms.js`) uses those Thai labels on the pills so “แก้ได้หรือยัง” is explicit.
- **Run `sql/harden_security.sql` in Supabase SQL Editor if not already applied — it's idempotent, safe to re-run any number of times.** Fixes, in order: (1) profiles self-role-escalation — `profiles: update own` had no column restriction, so any logged-in user could set their own `role` to `'admin'` via a direct Supabase call; now a trigger blocks self-changes to `role`/`is_active` unless already admin; (2) `business_config` writes tiered by key — `role_perms`/`opex_defaults` admin-only, `emp_details`+`form50_payees` admin+co-admin, everything else (`biz_info`, `emp_pay_history`, etc.) unchanged/open; (3) `audit_log` reads restricted to admin; (4) `sales_daily`/`expenses` UPDATE restricted to admin/co-admin/manager (excludes `staff` — staff can still INSERT new entries, just not edit existing ones); (5) `business_config` changes now audit-logged too (see below).
- **⚠️ RLS gotcha discovered 2026-07-19: Postgres RLS `UPDATE ... USING` (no `WITH CHECK`) fails silently, not loudly.** If a row already exists and the caller's role fails the `USING` clause, the UPDATE matches **zero rows** — no error, `error` stays `null`. `.upsert()` calls that don't `.select()` can't even detect this, so a blocked save just looks like "the button does nothing." All `business_config` upserts now go through `lib/config-store.js` `upsertBusinessConfig()`, which `.select('key')` and treats an empty result as a permission error. **Any new `business_config` write must use this helper**, not a bare `.upsert()`. Also: `emp_pay_history`'s RLS tier must always match whatever role can trigger `saveOpexAction` (currently any authenticated user) — restricting it tighter than that silently breaks pay-history recording for non-admin OPEX saves, which is exactly what happened before this fix. UI now also disables (not just hides) `emp_details`/`form50_payees` edit fields for roles that can't save them, so the mismatch fails visibly and early instead of silently at submit time.
- `audit_log` (with `old_data`/`new_data`, trigger-populated, `SECURITY DEFINER` so it can't be forged by clients) tracks every INSERT/UPDATE/DELETE on `sales_daily`, `expenses`, `profiles` (role/active), `business_config`, and (after `add_audit_context.sql`) loyalty `customers` (name/phone/LINE only — not every points-balance tick), `point_transactions`, `redemption_history`. **Context (IP, User-Agent, device summary, path, country)** is stamped via `set_audit_context` from Server Actions then copied by the trigger; auth/admin events (login success/fail, logout, deny, export, import, user admin) go through `write_audit_event`. **Do not log passwords.** Viewable at **`/admin/audit`** — **Super Admin (`role = admin`) only**, not co-admin (sidebar + page redirect + RLS). Filter by table/action/IP/username; page size **10 / 20 / 50 / 100** (default 20). IP + device show **under the username on the right** of each row, full User-Agent when the row is expanded — blank on rows written *before* the SQL/context was applied (expected). **Requires `sql/add_audit_context.sql`.** `business_config`'s primary key is `key` (text), not `id` — `fn_audit_log_config()` stores `record_id` null; the key is in JSON. Helpers: `lib/request-meta.js`, `lib/audit.js`.
- **Form 50 ทวิ payee editing (`app/opex/form50.js`) moved from admin-only to admin+co-admin on 2026-07-20** — matches `emp_details`'s existing tier. Prop renamed `isAdmin` → `canEdit` throughout that file to reflect this (still admin-only in the RLS sense for `role_perms`/`opex_defaults`, just not for `form50_payees` anymore).
- **Money/quantity inputs — `components/number-input.js` (`NumberInput`), mandatory since 2026-08-25.** Every price/amount/quantity/points field in the app now renders `<input type="text" inputMode="decimal|numeric">`, **never `type="number"`**. Reason: the native number input's spinner arrows are easy to mis-click, and worse, **scrolling the mouse wheel over a focused number input silently changes the value** — a real risk for money entry (a wheel flick while scrolling the OPEX/sales page could turn 12,000 into 12,003 with nothing on screen to show it happened). `type="text"` has no spinner and ignores the wheel entirely, while `inputMode` keeps the numeric keypad on mobile. `NumberInput` also applies `sanitizeNumberString()` centrally, so call sites just pass `onChange={(v) => ...}` (a **string**, like `DateField` — not an event). Props: `value`, `onChange(value)`, `mode="decimal"` (default, allows a decimal point) or `mode="numeric"` (whole numbers: points, sort order), `align` (default `right`), `selectOnFocus` (default `true`); everything else (`className`, `style`, `placeholder`, `disabled`, `required`) passes through.
  - **Data-entry behavior baked into the component (the state value is always plain digits — the commas are display-only):** while the field is *not* focused it shows thousands separators via `groupNumberString()` (`lib/format.js` — unlike `fmtMoney()` it does not round and keeps the decimals exactly as typed, so `"12000.5"` shows as `"12,000.5"`); on focus it reverts to plain digits **and selects the whole field** so a monthly figure can be typed over without backspacing (matters most on `/opex`, ~20 prefilled amounts); text is right-aligned so a column of amounts lines up by place value. `selectOnFocus` runs inside `requestAnimationFrame` — it has to wait for React to paint the un-grouped value, otherwise `select()` grabs the string that is about to be replaced. Used by sales, expenses (form + inline edit), OPEX rows + payslip fields, settings (biz info + OPEX defaults), loyalty earn, and the admin rewards catalog. `app/globals.css` also hides webkit/moz spinners on any stray `input[type="number"]` as a safety net, but **do not rely on it — use `NumberInput`.** Fields where a leading zero is meaningful (phone, national ID, bank account, tax id) stay plain `type="text"` + `digitsOnly()` — they are not numbers.
- **Numeric input sanitization (`lib/format.js`, added 2026-07-20):** `sanitizeNumberString()` strips leading zeros live while typing (`"0123"` → `"123"`, but keeps `"0"` and `"0.5"` intact) and strips any character that isn't a digit or a decimal point — this blocks `e`/`+`/`-` which native `<input type="number">` otherwise accepts (typing `"1e5"` would silently become a huge number). Applied to every money/quantity input in the app, either centrally (wherever a shared `set(k)`-style handler exists — `sales-form.js`, `opex-form.js`'s `Row`/`SlipField` components) or at the individual call site where the handler is generic and shared with non-numeric fields (`expense-form.js`, `expense-list.js`, `settings-form.js`, `opex-defaults.js`). **Do not add a raw numeric `onChange={(e) => set(k, e.target.value)}` anywhere — use `NumberInput` (which sanitizes for you), or run the value through `sanitizeNumberString()` first.**
  - `stripDigits()` — for genuine person-name fields (employee `fullname`/`lastname`/`account_holder`, Form 50 payee `name`, admin user `full_name`/`nickname`) so a name field can't end up containing digits.
  - `digitsOnly()` — for fields that must be numeric but where a leading zero is meaningful and must NOT be stripped (Thai national ID `id_card`, bank `account_no`, Form 50 `taxid`, and — added 2026-08-25 — the business `tax_id` on `/settings`, which was the last one still accepting letters despite its `maxLength={13}`) — distinct from `sanitizeNumberString()`, which is only for money/quantity values where leading zeros are meaningless. These stay plain `type="text"` (+ `inputMode="numeric"`), **not** `NumberInput` — they are digit strings, not numbers. The `/settings` phone field is deliberately left free-form: the `0xx-xxx-xxxx` placeholder means dashes are intentional there.
  - Deliberately **not** applied to item/product/supplier name fields (expense `item_name`, `supplier`) — those legitimately contain digits (e.g. "นมสด UHT 1L", "แก้ว 12oz").
- Password minimum length is `MIN_PASSWORD_LENGTH` in `lib/auth-policy.js` (currently 8), enforced in `createUserAction`/`resetPasswordAction`. **Also set the same (or higher) minimum in Supabase Dashboard → Authentication → Providers → Email → Minimum password length** — the app-side check alone doesn't constrain Supabase Auth itself.

## Backups (off-site, 2026-08-26)

- **`scripts/backup-to-r2.sh` + `deploy/BACKUP.md`** — nightly `pg_dump` → `age`-encrypted → Cloudflare R2 (`ddservicedb` bucket, prefix `minimalcnx/daily/` and monthly copy `minimalcnx/monthly/`), run from cron (`0 20 * * *` = 03:00 ICT) on the VPS. `scripts/restore-from-r2.sh --drill` restores the latest backup into a throwaway Postgres container and prints row counts; **run it quarterly — a backup nobody has restored is not a backup.**
- **The dump is encrypted before it leaves the machine, and that is not optional.** It contains every customer phone number (`customers`), employee national-ID and bank-account numbers (`business_config.emp_details`) and tax IDs (`form50_payees`) — full PDPA-scope personal data, from a system that already asks customers for consent. Private key lives at `~/minimalcnx-backup.key` (chmod 600, outside R2 and backed up to password manager); if it sits next to the backups, nothing is encrypted.
- **Connection string: session pooler (`:5432`) or direct, never the transaction pooler (`:6543`).** `pg_dump` needs session state and a stable repeatable-read snapshot, which transaction mode cannot hold; the script rejects `:6543` with that explanation. Production Supabase pooler host for this project is `aws-1-ap-southeast-2.pooler.supabase.com:5432`.
- **`@supabase/ssr` speaks PostgREST over HTTPS, not the Postgres wire protocol — this repo opens zero direct Postgres connections.** So Supavisor pooler settings have **no effect on app latency**; that connection string exists only for backups. Don't "enable the transaction pooler to speed up the app" — it does nothing here.
- `pg_dump` covers `public` + `storage` **schemas but not Storage file contents** — `scripts/sync-storage-to-r2.sh` handles checking and syncing the `evidence` bucket (free-cup proof images). `auth.users` is deliberately out of scope (Supabase-managed, not portable across projects). Credentials (`.backup.env`, `*.key`) are gitignored.
- **Auto-trimming & Webhook Alerts:** `backup-to-r2.sh` automatically keeps `~/backup.log` under 2,500 lines (trims to latest 1,500) and supports optional `BACKUP_ALERT_WEBHOOK` for instant Discord/Slack/Telegram failure alerts. Restore drill container automatically pre-provisions `extensions` and `auth` schemas + `uuid-ossp` and `pgcrypto` before `pg_restore`.
- **90-Day Retention Policy (2026-08-28):** Cloudflare R2 bucket uses Object Lifecycle Rules (`minimalcnx/daily/` expires after 90 days). `backup-to-r2.sh` and `scripts/vps-clean.sh` automatically purge any local backup dumps older than 90 days.
- **VPS Housekeeping & Auto-Prune (2026-08-28):** `deploy.sh` automatically prunes Docker dangling images and builder cache on each deploy. Run `bash scripts/vps-clean.sh` on the VPS for periodic system cleanup (Docker cache, journal logs vacuum to 100MB, `/tmp` purge, and local backup retention).

## Performance

- **`lib/session.js`'s `requireSession()` uses `getSession()`, not `getUser()` — deliberately, not an oversight.** `getUser()` makes a real network round-trip to Supabase's Auth server to re-verify the JWT; `getSession()` just reads/decodes it from cookies locally. `middleware.js` already calls `getUser()` (the network-verified, authoritative check) on every request before any page or Server Action runs, refreshing cookies if needed — by the time `requireSession()` runs, the cookies it reads via `lib/supabase/server.js` already reflect that verified session, so re-verifying with a second `getUser()` call was pure added latency (two Supabase Auth round-trips per page load instead of one) with no real security benefit. **If you ever see `requireSession()` using `getUser()` again, that's a regression — change it back to `getSession()`.** Note this optimization was deliberately *not* extended to the many standalone `supabase.auth.getUser()` calls inside individual Server Actions (`app/*/actions.js`) — those aren't on the page-load critical path (they run on form submit, not navigation) and touching auth checks across many mutation endpoints at once was judged higher-risk for lower payoff; revisit only if Server Action latency specifically becomes a complaint.
- **Two caches, two very different safety rules (added 2026-08-26). Getting these mixed up silently breaks RLS, so read this before caching anything new.**
  - **`lib/account.js` + `cache()` on `createClient()` — per-request dedupe.** React's `cache()` lives and dies inside one request, so it is safe for **user-scoped** data. `getProfile(userId)` is shared by `requireSession()` (`lib/session.js`) and `loadAccess()` (`lib/access.js`); a page that goes through both — `/loyalty/analytics` runs `requirePage()` and then `getLoyaltyAnalyticsAction()` — used to fetch the same profile twice. `createClient()` is cached too, so one Supabase client per request instead of one per caller. Pass **primitives** to a `cache()`d function (`getProfile(user.id)`, not `getProfile(supabase, id)`) — memoization compares arguments by reference.
  - **`lib/config-cache.js` — process-wide, 60s TTL, `business_config` only.** This one crosses users, which is only sound because policy `config: read authenticated` returns the *same rows to every logged-in user*. **Never extend this pattern to `sales_daily`, `expenses`, `customers`, `audit_log` or anything else RLS filters per user — caching a user-scoped result serves one person's data to another and defeats the whole security model.** It never caches errors or missing rows either: caching an empty `role_perms` would drop everyone to default permissions for a minute.
  - Invalidation has exactly one choke point: **`upsertBusinessConfig()` in `lib/config-store.js` calls `invalidateConfigCache(key)`**, which is why every `business_config` write must go through that helper (the `biz_info` save in `app/settings/actions.js` was bypassing it and now doesn't). The TTL is only a safety net for someone editing a value straight in Supabase Studio.
  - Reads go through **`readBusinessConfig(supabase, key, fallback)`** — used for `role_perms` (every page load), `opex_defaults` (`/dashboard`, `/reports`, `/analytics`) and `biz_info` (`/sales`). `unstable_cache` was rejected deliberately: its callback may not touch dynamic APIs, and the server Supabase client reads cookies when it issues a request.
- **Icons are tree-shaken React SVGs (`@tabler/icons-react` via `components/icon.js`), not the full webfont.** Previously `@tabler/icons-webfont` shipped every glyph in CSS+font files on every page. Now only icons that appear in the JS graph are bundled. Use `<Icon name="ti-xxx" />` (or pass `ti-xxx` into `PageHeader`/`Kpi`). **Never add a CDN `<link>` for an icon set — and do not re-introduce the full webfont package.**
- **⚠️ Fix (2026-08-27, `app/sales/actions.js`, `app/expenses/actions.js`, `app/opex/actions.js`):** Added `revalidatePath('/analytics')` and `revalidatePath('/reports')` across all write endpoints so reports, dashboard, and analytics reflect fresh DB data immediately without serving stale Router Cache RSC payloads.
- **⚡ Fixed (2026-08-27): `/reports` MonthPicker June/July sluggish / unresponsive selection resolved system-wide:**
  - **Root Cause 1 (Client UX & React Transitions):** `MonthPicker` (and `RangePicker`) did not use `useTransition` or local optimistic state. When picking a month (June/July), the controlled `DateField` remained displaying the old month while the server component fetched the heavy payload. Because there was zero visual feedback, users repeatedly clicked, interrupting/cancelling active React transitions, resulting in "nothing happens / works intermittently / takes long". Fixed by adding optimistic local state + `useTransition` + `loading` spinner on `DateField` across `MonthPicker`, `RangePicker`, `ExpenseForm`, `ExpensesClient`, `SalesForm`, and `OpexForm`.
  - **Root Cause 2 (Database Query Plan & Payload Size):** June and July contain hundreds of real itemized rows (unlike empty months). `get_monthly_summary`'s compound `OR` condition across `date` and `month_label` prevented direct index scans. Fixed via `sql/optimize_queries.sql` by restructuring the query to use `UNION ALL` (allowing separate index scans on `idx_expenses_date_item_null` and `idx_expenses_month_opex`) and optimizing `get_months_kpis` for `/analytics`. Run `sql/optimize_queries.sql` in Supabase SQL Editor.
  - **Architecture Speedup (`app/reports/reports-client.js` + `actions.js`):** Added in-memory client-side cache and automatic background prefetching for preceding months (July, June). Once prefetched, switching to June/July happens in **0ms (instantly from memory)** with zero network delay and zero layout flash. Itemized monthly expenses table includes **Pagination (10 / 20 / 50 / 100 / ทั้งหมด)**, Category filter dropdown, and real-time instant search to eliminate DOM render bottlenecks and provide smooth data navigation.

## Domain formulas (keep identical to legacy)

- Delivery GP rates: shopee 0.3424, grab/lineman 0.321. `net = raw × (1 − rate)`. (`lib/gp.js`)
- `sales_daily.net_revenue` = kshop + cash + delivery(after GP). Pastry & free-cup cost stored separately.
- Expense VAT 7%: `total = price × 1.07 × qty` when VAT on (baked into `total_amount`, not stored separately).
- OPEX rent WHT: pay owner 95%, withhold 5% (remit to Revenue Dept). Stored amount = full rent.
- OPEX VAT-auto suggestion = month net sales × 7%.
- Payroll (`payslip()` in `app/opex/opex-form.js`): SSO 5% of min(salary,15000) for employee AND company; commission = income × rate; commission tax 3%; gross = salary+position+commission+diligence; net transfer = salary−ssoEmp+position+diligence+(comm−commTax); **saved OPEX amount = companyCost = gross + companySSO**. **(2026-07-20) The per-employee OPEX amount is no longer a manually-typed field** — it used to require opening "คำนวณเงินเดือน" and clicking a separate "ใช้ยอดนี้" button to copy `companyCost` in, which was easy to forget (an employee's cost could silently stay at a stale/₿0 figure for a whole month). It's now computed live from `payslip(e, income).companyCost` on every render and at submit time — there is no independent `amount` state for employees anymore, so editing salary/position/commission/diligence updates the displayed and saved OPEX figure immediately with no extra step.
- **⚠️ Fixed 2026-08-25 — `computeEffectiveOpex()` had its own copy of the employee cost and it disagreed with the payslip.** The auto-filled default for emp1 was hardcoded `13000 + 1500 + 725`, i.e. SSO taken as 5% of 14,500 (salary + position), while `computePayslip()` correctly uses 5% of `min(salary, 15000)` = 13,000 → 650. emp2 happened to be right. Net effect: every month with no OPEX rows saved yet reported **75 ฿ more expense than `/opex` would actually save**, on `/dashboard`, `/reports` and `/analytics`. It now calls `computePayslip(...).companyCost`, so there is exactly one payroll formula in the codebase. `tests/opex.test.mjs` pins both employees' expected cost against the payslip, so the two can't drift again.
- Employee defaults (`DEFAULT_EMPLOYEES`, `lib/opex.js`): emp1 13000/1500, emp2 12000/0; salary_dir default 36000. Payslip inputs persist in `localStorage` (`mm69_emp_slip`).

## Design system (2026-07-20 redesign — soft/modern, sidebar layout)

**Everything is driven by CSS custom properties defined once at the top of `app/globals.css` (`:root`).** To retheme the whole app, edit values there only — never hardcode a color/radius/shadow in a component.

- **Brand tokens:** `--color-primary` (coffee, primary actions/active states), `--color-accent` (taupe, highlights/focus). Swap these two to rebrand entirely.
- **Neutrals:** `--color-bg` (page canvas), `--color-surface`/`--color-surface-2`, `--color-border`, `--color-text`/`--color-text-muted`.
- **Radius scale:** `--radius-sm` (8px) / `--radius-md` (12px, default for cards/inputs/buttons) / `--radius-lg` (16px, cards/login) / `--radius-full` (pills/badges/chips). This is *the* lever for "soft vs boxy" — the previous Swiss-style redesign used a flat 2px everywhere, which read as rigid; this pass replaced it app-wide.
- **Shadow scale:** `--shadow-sm`/`--shadow-md`/`--shadow-lg` — soft, layered, multi-stop shadows instead of hard 1px borders for depth.
- **Legacy aliases:** `--coffee`, `--taupe`, `--border`, `--surface`, etc. all map onto the tokens above, so the many components using inline `style={{ ...: 'var(--coffee)' }}` continue to work without edits.
- **Inline-style radius:** components still use inline `style={{}}` objects (not just `className`) for layout-specific spacing — but every `borderRadius` value in those objects is `'var(--radius-md)'` (or `--radius-full` for true pills), never a hardcoded number. Grep for `borderRadius: [0-9]` before adding new inline styles — if you find a literal number, that's a bug, use a token.

**Layout — sidebar shell, not the old top-tab bar:**
- `components/app-shell.js` (client component — needs `mobileOpen` state + `usePathname`) renders `<div class="shell"><Sidebar .../><div class="shell-main"><div class="mobile-topbar">...</div><div class="desktop-topbar">...</div><div class="shell-container">{children}</div></div></div>`.
- **⚠️ Gotcha (2026-07-20): `.mobile-topbar` must be an actual DOM child of `.shell-main`, never a flex sibling of `.sidebar` inside `.shell`.** An earlier version rendered it as a top-level sibling returned by `Sidebar` (so it became a flex item of `.shell`, a row-flex container, alongside `.shell-main`). On real iPhone Safari this caused `.mobile-topbar` to shrink-to-fit instead of taking its own row (tried `flex-wrap:wrap` + `width:100%` first — spec-correct but Safari didn't reliably honor it), squeezing `.shell-main` into a sliver and wrapping KPI numbers one digit per line. Fixed by moving `.mobile-topbar` to be a literal child of `.shell-main` (a column-flex container, so `align-items:stretch` gives it full width unconditionally — no flex-wrap dependency at all). **`mobileOpen` state now lives in `AppShell`** (passed down to `Sidebar` as `mobileOpen`/`setMobileOpen` props) since both the hamburger button (in `.mobile-topbar`, inside `.shell-main`) and the drawer/overlay (in `Sidebar`, a `.shell` sibling of `.shell-main`) need to share it, and they're no longer in the same DOM subtree.
- `components/sidebar.js` (client) renders `lib/perms.js` `NAV_TABS` (same source of truth as before) as a **collapsible left rail on desktop** (icon-only toggle, state remembered in `localStorage` key `mm69_sidebar_collapsed` — pure UI preference, not business data, so this doesn't violate the localStorage rule elsewhere in this doc) and a **slide-in drawer on mobile** (`<960px`, hamburger trigger + backdrop overlay, auto-closes on route change). Only renders the overlay + `<aside>` now — no longer owns `mobileOpen` (see above) or renders `.mobile-topbar` itself.
- `app/loading.js` — **Global Skeleton Loader for Next.js App Router**: Provides 0ms instant visual feedback on menu navigation while Server Components fetch DB data in the background.
- `.desktop-topbar` (≥961px only) shows the logged-in user's name/role — the one piece of session context that's otherwise hidden when the sidebar is collapsed to icon-only (`.sidebar-brand-text` hides in that state). Real session data only (`name`/`role` props `AppShell` already receives) — no fabricated notification bell/badge; don't add one without an actual notification data source behind it.
- `.wrap` class still exists (aliased to the same container styles) for anything not going through `AppShell`.

**KPI tiles — `components/kpi.js`:** icon-in-a-circle on the left, label/value/sub stacked on the right (`<Kpi icon="ti-xxx" label="..." value="..." sub="..." cls="green|red|blue" plain />`). Single shared component used by `dashboard`, `reports`, `analytics` — previously 3 near-duplicate inline implementations (one of which formatted money *inside* the component, two of which expected pre-formatted strings). All callers now pre-format via `fmtMoney()` before passing `value`. **`.kpis` uses fixed column counts per breakpoint (1/2/3), not `auto-fit`** — `auto-fit` packs as many columns as physically fit a wide desktop screen (e.g. 5), so a page with a tile count that isn't a clean multiple of that (dashboard has 6) left a dangling last row with several empty column-widths of blank space beside the orphaned tile. Fixed columns mean tile counts always wrap into clean, evenly-filled rows regardless of screen width.

**Date/month fields — `components/date-field.js`, mandatory for any new date or month picker:**
- **⚠️ Gotcha: iOS Safari (WebKit) does not allow full CSS control over `input[type=date]`/`input[type=month]` internals.** Setting `background`/`color` works, but a native hairline/chrome inside the control still renders and can't be removed — not via `overflow:hidden` on the input (native widget paint mostly ignores its own `overflow`), not via a wrapping `overflow:hidden` div either (fixes gross bleed/overlap onto neighboring fields, but doesn't fix the internal hairline).
- `DateField` sidesteps this rather than fighting it: the real `<input type="date"|"month">` is still there and still fully drives interaction (opacity:0, absolutely positioned over a plain `<span>` that we fully control and style to match every other input exactly). Props: `value`, `onChange(valueString)` (not an event — different from a raw `<input onChange>`), `type="date"|"month"`, `min`, `max`, `disabled`, `placeholder`.
- **⚠️ Gotcha: this overlay technique broke picker-opening on desktop while working fine on mobile.** iOS opens its native wheel picker on a tap anywhere in the input; desktop Chrome/Edge/Firefox only open the dropdown when the click lands on the native input's own small calendar-icon hotspot (clicking the text area just places a keyboard cursor) — hiding the whole input at `opacity:0` hides that hotspot with no visual cue for where it is, so desktop users had no way to open the picker at all. Fixed by calling `inputRef.current.showPicker()` on click of the wrapper (any click position), which works cross-browser wherever `showPicker()` is supported (falls back to native click-through behavior where it isn't).
- Used by all 7 date/month fields in the app: sales, expenses, analytics range picker, opex month + Form 50 date, reports month picker, settings data-tools. **Do not add a raw `<input type="date">`/`type="month">` anywhere — use `DateField`.**

**⚠️ Gotcha (2026-07-20): forms that pre-fill from a date/month-scoped `existing` prop need `key={date}` (or `key={monthInput}`) on the component, not just the prop.** `SalesForm`/`OpexForm` initialize their fields via `useState(() => ...existing)`, which only runs on first mount. Changing the date/month via the URL re-fetches `existing` server-side and passes new props down, but React doesn't remount the client component just because props changed (same position in the tree) — so the *old* date's field values stayed frozen on screen while the newly-fetched data was silently ignored (reported as "picking a past date shows a blank form even though I already entered data for it"). `key={date}`/`key={monthInput}` on `<SalesForm>`/`<OpexForm>` in `page.js` forces a clean remount (and full state reset) on every date/month change — the standard React fix for this exact class of bug. `Form50` doesn't need this: its own state (payee info) is intentionally month-independent, and `amounts` are read reactively from props each render rather than copied into state.

**Responsive tables — `components/data-table.js`:**
- Desktop: renders a normal `<table>`. Mobile (`<720px`): pure-CSS transform (`.rtable` rules in globals.css) turns each row into a bordered, shadowed card with `data-label` pseudo-labels — no JS breakpoint logic.
- Usage: `<DataTable columns={[{key,label,align,render?}]} rows={[...]} rowKey={(r) => ...} />`. Applied to `/reports` (category breakdown) and `/analytics` (top materials, monthly comparison) as the reference implementations. **Other raw `<table>` usages in the app (e.g. `/admin/audit` inline diff table) were left as-is** (horizontal-scroll on mobile, still functional) — convert them to `DataTable` opportunistically when touching those files, not urgent.

**⚠️ Gotcha (2026-07-19, `app/layout.js`): a custom `export const viewport` object REPLACES Next.js's default viewport meta tag entirely — it does not merge.** Omitting `width`/`initialScale` silently breaks mobile rendering (iOS Safari falls back to the ~980px legacy desktop viewport, shrinking the whole page). Always include `width: 'device-width', initialScale: 1` alongside any custom `themeColor` etc.

**Added (2026-07-28, `app/expenses/actions.js` + `expense-form.js`): duplicate-entry warning on save.** Root cause of a real incident — material-cost total for 07/2026 was ~120,000 ฿ when staff's own manual count said ~70,000 ฿ — turned out to be duplicate rows (same date+category+item_name+total_amount logged more than once), the same class of bug `dedupMonthAction` (`app/settings/actions.js`) already exists to clean up after the fact. - **`sql/harden_loyalty_integrity.sql` — run last in the loyalty chain (after `add_loyalty_rewards.sql`)** (idempotent). Fixes five data-integrity holes at once, all of which the app already falls back gracefully from if it isn't applied yet:
  1. **`fn_rfm_segment(visit_count, last_visited_at)`** — the RFM formula, previously inlined in the trigger, is now one SQL function. **Its JS twin is `lib/rfm.js` — change one, change the other** (`tests/loyalty.test.mjs` pins the thresholds).
  2. **`fn_on_point_transaction()` no longer counts `adjust` rows as visits.** Voiding a transaction used to *increment* `visit_count` and push `last_visited_at` forward — i.e. cancelling a mistaken earn made the customer look *more* active. Visits/last-visit now count `earn`+`redeem` only; the points balance still sums every row (a void must move points). Includes a one-time backfill that temporarily disables `tr_customers_guard_points` (that guard blocks points writes at `pg_trigger_depth() = 0`, which is where a migration runs).
  3. **`get_loyalty_segment_counts()`** — returns total members, points outstanding, and per-segment counts computed **live** in SQL. `/loyalty/analytics` used to pull every `customers` row into Node to count them (slow as the base grows, and silently truncated if the project sets `db-max-rows`) *and* read the stale `rfm_segment` column. **The stale column was the real bug: the trigger only fires when a transaction arrives, but a lapsing customer is by definition one with no transactions — so nobody ever became `At-Risk`/`Lost`.** The app now computes segments live everywhere (`lib/rfm.js` for the single-customer badge, this RPC for the dashboard); the stored column is advisory only.
  4. **`uidx_point_tx_earn_receipt`** — unique partial index on `(branch_id, lower(trim(receipt_number))) where transaction_type = 'earn'`. The receipt number was mandatory but never checked, so one bill could be used to earn points repeatedly (the rate limiter only catches ≥5 earns to the *same* customer in 10 min). `issuePointsAction` pre-checks it for a readable message (which bill, when, to whom) and logs `FRAUD_ALERT_DUPLICATE_RECEIPT`; the index is the real guard and its `23505` is handled too. **If duplicates already exist the file skips creating the index and raises a NOTICE with the count** rather than failing — void the duplicates, then re-run.
  5. **`loyalty_redeem_reward(customer, reward, branch)`** — `SECURITY DEFINER`, does the points row + `redemption_history` + audit in one transaction with `select … for update` on the customer. Previously these were separate inserts: if the second failed, points were gone with no redemption record.
