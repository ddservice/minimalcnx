# Feature status, history, incident notes (moved verbatim from CLAUDE.md 2026-10-12)

## Feature status vs legacy

**Added (2026-07-28, `app/expenses/actions.js` + `expense-form.js`): duplicate-entry warning on save.** Root cause of a real incident — material-cost total for 07/2026 was ~120,000 ฿ when staff's own manual count said ~70,000 ฿ — turned out to be duplicate rows (same date+category+item_name+total_amount logged more than once), the same class of bug `dedupMonthAction` (`app/settings/actions.js`) already exists to clean up after the fact. This adds a **before-the-fact** check: `saveExpensesAction` now queries same-day+same-category expenses first and, if any submitted row matches an existing one on `item_name` (case-insensitive trim) + `total_amount` — the same key `dedupMonthAction` uses — returns `{status:'confirm', message}` instead of inserting. The client (`expense-form.js`) shows this as a `window.confirm()`; on OK it resubmits with `force:true` to skip the check and insert for real. **Deliberately a soft warning, not a hard block** — legitimately buying the same item at the same price twice in one day does happen, so it must stay overridable.

**⚠️ Fix (2026-07-28, `app/expenses/expense-list.js` + `expenses-client.js`):** the "รายการที่บันทึกแล้ว" list under the expense form used to be filtered to whichever category tab was active (`allExisting.filter(e => e.category === category)`), and the page always opens on the first category tab by default. A staff member who logged an expense under one category and reopened the page later (defaulting back to tab 1) saw an empty list and assumed their entry was lost/never saved. Fixed by showing **all categories' entries for the date** in the list (unfiltered), with a small category badge per row (`CATEGORY_LABEL` map from `lib/expense-categories.js`) so it's still clear which tab each row belongs to. The day's total at the bottom is now a cross-category total, labeled accordingly. Editing a row still preserves its original category (`updateExpenseAction` never touches `category`), so this is purely a display fix, no schema/action change.

**⚠️ Lesson learned (2026-07-19):** employee personal/bank details (name, ID card, bank account) were originally stored **only in browser localStorage** (`mm69_emp_slip`), matching the legacy dashboard's pattern. **Fixed (2026-10-12, `app/expenses/expense-form.js`): double-submit on the expense form.** The save button was only disabled by `isPending`, which covers the `router.refresh()` transition *after* the Server Action returns — during the request itself the button stayed live and showed no "กำลังบันทึก...". Real incident 2026-09-29: while backfilling September material costs, two whole batches (07/09 and 14/09) were inserted twice 4–5 seconds apart (visible in `audit_log` as identical INSERT groups), then cleaned up row by row by hand — and that manual cleanup also removed 15/09 entirely plus two 27/09 rows, which is what was reported as "saved but the total did not update". Nothing was lost by the system; `audit_log` showed every insert and every delete. Fix: a `savingRef` guard (a ref, because state alone is too slow to stop a double-tap) + `saving` state that disables the button and shows "กำลังบันทึก..." for the whole request, and a `try/catch` so a thrown action (network drop, action-ID mismatch right after a deploy) shows an error instead of nothing. **When investigating "my entry disappeared", query `audit_log` for `table_name = 'expenses'` first** — the time column is `performed_at`, the actor is `performed_by` → `profiles.id`.

**Fixed (2026-10-12, `app/expenses/actions.js`): half-filled expense rows are rejected, not dropped.** `saveExpensesAction` used to filter out any row missing a name or a price and save the rest, then the form reported success and cleared every row — the dropped line vanished with nothing on screen. It now returns an error naming the row numbers (same numbering as the form's "รายการที่ N") and saves **nothing** until they are completed or removed. Rows with neither a name nor a price are still ignored (the form always carries one blank row).

**Rebuilt (2026-10-12, `app/opex/form50.js` + new `lib/wht.js`): Form 50 ทวิ now follows the Revenue Department layout.** The first version had never been used in production (both payees were still empty) and was not fit to hand to a landlord. What changed, and why each matters:
  - **Layout:** เล่มที่ / เลขที่, three copies per print (ฉบับที่ 1–2 for the payee, 3 for the shop), 13-digit tax IDs for both sides, the "ลำดับที่ … ในแบบ" checkboxes (ภ.ง.ด.1ก … ภ.ง.ด.53), all six income rows with the amount placed in **row 5** (payments under section 3 เตรส — rent / service), total row, baht text, the fund line, payer-condition checkboxes, the legal warning, the certification sentence, payer signature, issue date and seal box. The payee signature block is gone — the official form has none. Row 4 (ข) is condensed to one line; the official form breaks dividends into sub-rates the shop never uses.
  - **`paidDates` — the actual payment date, per month** (`form50_payees.<item>.paidDates['MM/YYYY']`). The old template printed the *print date* in the "date paid" column, so a certificate printed late carried the wrong date and could fall in the wrong tax month. Printing is refused until the month's payment date is set.
  - **Condition numbers were swapped.** Official order is (1) หัก ณ ที่จ่าย (2) ออกให้ตลอดไป (3) ออกให้ครั้งเดียว; the old code had 2 and 3 the other way round. Stored `cond` values now mean the official numbers — safe because nothing had been saved yet.
  - **`computeWht(amount, rate, cond)`** (`lib/wht.js`, pinned by `tests/wht.test.mjs`): (1) tax = amount × rate; (2) tax = amount × rate ÷ (1 − rate), income = amount + tax; (3) income = amount × (1 + rate), tax = income × rate.
