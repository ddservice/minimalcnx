# Backups and moving Supabase projects (moved verbatim from CLAUDE.md 2026-10-12)

## Backups (off-site, 2026-08-26)

- **`scripts/backup-to-r2.sh` + `deploy/BACKUP.md`** — nightly `pg_dump` → `age`-encrypted → Cloudflare R2 (`ddservicedb` bucket, prefix `minimalcnx/daily/` and monthly copy `minimalcnx/monthly/`), run from cron on the VPS. **That VPS's clock is `Asia/Bangkok`, not UTC, so cron entries are already Thai time** — `0 20 * * *` fires at 8pm ICT (verified 2026-09-09 against `timedatectl` and the 13:00Z stamps in `~/backup.log`); this doc used to claim it meant 03:00 ICT, which was wrong in both directions. The storage sync runs 20 minutes later at `20 20 * * *`. Left at 8pm deliberately: 3am already carries two other projects' backup jobs on the same box, and this dump is ~375 KB. `scripts/restore-from-r2.sh --drill` restores the latest backup into a throwaway Postgres container and prints row counts; **run it quarterly — a backup nobody has restored is not a backup.**
- **The dump is encrypted before it leaves the machine, and that is not optional.** It contains every customer phone number (`customers`), employee national-ID and bank-account numbers (`business_config.emp_details`) and tax IDs (`form50_payees`) — full PDPA-scope personal data, from a system that already asks customers for consent. Private key lives at `~/minimalcnx-backup.key` (chmod 600, outside R2 and backed up to password manager); if it sits next to the backups, nothing is encrypted.
- **Connection string: session pooler (`:5432`) or direct, never the transaction pooler (`:6543`).** `pg_dump` needs session state and a stable repeatable-read snapshot, which transaction mode cannot hold; the script rejects `:6543` with that explanation. Take the pooler host from Supabase Dashboard → Connect → Session pooler for the **current** project (`ap-southeast-1` since the 2026-09-09 move) — the `aws-1-ap-southeast-2…` host this doc used to name belongs to the old Sydney project.
- **`@supabase/ssr` speaks PostgREST over HTTPS, not the Postgres wire protocol — this repo opens zero direct Postgres connections.** So Supavisor pooler settings have **no effect on app latency**; that connection string exists only for backups. Don't "enable the transaction pooler to speed up the app" — it does nothing here.
- `pg_dump` covers `public` + `storage` **schemas but not Storage file contents** — `scripts/sync-storage-to-r2.sh` copies the `evidence` bucket (free-cup proof images) to `minimalcnx/storage/evidence/<name>.age`, `age`-encrypted like the DB dump, skipping objects already on R2 (filenames carry a timestamp so they're immutable). `--dry-run` lists what it would upload. **⚠️ Fixed 2026-09-09: this script was a stub** — it listed `storage.objects`, printed "ซิงค์เสร็จสิ้น" and uploaded nothing, so every free-cup evidence image was unbacked while the log said otherwise. It also needs `SUPABASE_URL` (the `https://<ref>.supabase.co` Storage API host, derived from `SUPABASE_DB_URL` when absent), not just the Postgres connection string.
- **`auth.users` is out of scope for the nightly backup** (Supabase-managed) — but it *is* migrated when moving projects, see below. A restore from R2 alone gives you data with no logins.
- **Auto-trimming & Webhook Alerts:** `backup-to-r2.sh` automatically keeps `~/backup.log` under 2,500 lines (trims to latest 1,500) and supports optional `BACKUP_ALERT_WEBHOOK` for instant Discord/Slack/Telegram failure alerts. Restore drill container automatically pre-provisions `extensions` and `auth` schemas + `uuid-ossp` and `pgcrypto` before `pg_restore`.
- **90-Day Retention Policy (2026-08-28):** Cloudflare R2 bucket uses Object Lifecycle Rules (`minimalcnx/daily/` expires after 90 days). `backup-to-r2.sh` and `scripts/vps-clean.sh` automatically purge any local backup dumps older than 90 days.
- **VPS Housekeeping & Auto-Prune (2026-08-28):** `deploy.sh` automatically prunes Docker dangling images and builder cache on each deploy. Run `bash scripts/vps-clean.sh` on the VPS for periodic system cleanup (Docker cache, journal logs vacuum to 100MB, `/tmp` purge, and local backup retention).

## Moving Supabase projects / regions (2026-09-09)

**Supabase cannot change a project's region — you create a new project and move the data across, which changes project ref, URL, anon key, service_role key and JWT secret.** Runbook: **`deploy/MIGRATE-REGION.md`** (Thai, copy-pasteable, run on the VPS). **Done 2026-09-09:** `fkhfrylvronkmktlmmia` (`ap-southeast-2` Sydney) → `vrmaquzhehbfqlfvrsxj` (`ap-southeast-1` Singapore). Rehearsed first with the shop open (`--dump` is read-only and `--load` targets an empty project), then re-run for real with the container stopped; row counts matched on all 17 tables, `auth` loaded with zero errors, and the `evidence` bucket turned out to hold 0 files so the storage step was skipped entirely.

- **`scripts/migrate-supabase-project.sh`** — `--check` / `--dump` / `--load` / `--verify` / `--all`. Reads `.migrate.env` (gitignored). Differs from `backup-to-r2.sh` in two ways that matter: it **does not pass `--no-privileges`** (the nightly backup does), because `grant execute … to authenticated` is what every RPC depends on — drop those grants and the whole app silently stops working; and it **dumps `auth.users` + `auth.identities`** so UUIDs and bcrypt password hashes come across, keeping `profiles.id` / `staff_profiles.user_id` / `audit_log.user_id` valid and letting everyone log in with their existing password.
- **Data is loaded with `session_replication_role = replica`, and that is not optional.** With triggers live, `fn_on_point_transaction` recomputes `points_balance` on top of the imported values, `tr_customers_guard_points` *blocks* the `customers` insert entirely, the audit triggers fabricate tens of thousands of `audit_log` rows dated today, and `tr_expenses_month_label` overwrites `month_label`. The GUC is set via `psql -c` in the **same session** as the `-f` data load — which is also why **transaction pooler `:6543` is rejected on both sides** (it swaps backends between statements, so the setting evaporates mid-load and the triggers come back with no error to show for it).
- Schema is dumped for **`public` only**. `auth` / `storage` / `extensions` belong to the Supabase platform and already exist in the new project at possibly a different version — dumping over them is how you break a fresh project.
- **`scripts/migrate-storage-files.sh`** — `--copy` re-uploads the `evidence` bucket through the Storage API (needs the new project's `service_role` key, used once from the VPS shell, never shipped to the browser), `--relink` rewrites `sales_daily.free_cup_evidence_url`. **The relink step is mandatory:** that column stores the full URL with the project ref inside it, so a DB-only migration leaves every evidence image loading from the old project and breaking the moment it's deleted.
- **`deploy.sh` no longer hardcodes the Supabase target.** It sources `.deploy.env` (gitignored, **required — no fallback**, see "Shared backend" above), prints `==> Supabase: <url>` before building, and rejects a key that doesn't look like a publishable/anon key. Remember `NEXT_PUBLIC_SUPABASE_*` is **baked into the client JS at `docker build` time** (see `Dockerfile`) — changing it always requires a rebuild, and pointing at the wrong project produces no error, just an app talking to the wrong database.
- What does **not** come across and must be re-set by hand on the new project: Auth settings (**Confirm email must stay OFF** — users live on the unroutable `@marim69.internal` realm and would never be able to confirm; minimum password length 8 to match `MIN_PASSWORD_LENGTH`), Site URL, the anon/service_role keys, and `.backup.env`'s `SUPABASE_DB_URL` (forget that one and cron keeps backing up the abandoned project every night, silently). The JWT secret changes too, so everyone is logged out once — passwords still work.
