**Migrations to run once (if not already applied):**
- **`sql/check_migrations.sql` — รันก่อนเสมอเพื่อดูว่าไฟล์ไหนรันไปแล้ว.** Read-only; returns one row of `true`/`false`, one column per migration below, detected by the object each file creates (trigger / RPC / index / column / policy) rather than by any bookkeeping table — so it works even on a project where nobody tracked what was applied. Use it instead of guessing from `CLAUDE.local.md`'s checkboxes.
- **`sql/add_loyalty_system.sql` — required for `/loyalty`.** Creates Loyalty/CDP tables, trigger, RLS, seed branches. Policies are idempotent (`drop policy if exists`). If you already ran an older copy before staff_profiles policies existed, also run `sql/fix_loyalty_staff_profiles_rls.sql`.
- **`sql/add_audit_context.sql` — ขยาย audit_log (IP / เครื่อง / path / login)** รันหลัง `harden_security.sql` แล้ว Super Admin ดูได้ที่ `/admin/audit`. Idempotent. ถ้าไปรัน `harden_security.sql` ซ้ำทีหลัง ให้รันไฟล์นี้ตามอีกครั้ง.
- **`sql/harden_loyalty_rls.sql` — run after add_loyalty_system.sql** (idempotent). Blocks client-side points tampering on `customers`.
- **`sql/harden_loyalty_writes.sql` — run after harden_loyalty_rls.sql** (idempotent). Tightens earn/redeem INSERT policies + `loyalty_void_transaction` RPC for voids.
- **`sql/add_loyalty_indexes.sql` — run after loyalty tables exist** (idempotent). Speeds history/CDP queries.
- **`sql/harden_loyalty_reads.sql` — run after loyalty tables exist** (idempotent). Restricts loyalty reads to staff with `staff_profiles` or manager+.
- **`sql/harden_loyalty_integrity.sql` — run last in the loyalty chain (after `add_loyalty_rewards.sql`)** (idempotent). Fixes five data-integrity holes at once, all of which the app already falls back gracefully from if it isn't applied yet:
  1. **`fn_rfm_segment(visit_count, last_visited_at)`** — the RFM formula, previously inlined in the trigger, is now one SQL function. **Its JS twin is `lib/rfm.js` — change one, change the other** (`tests/loyalty.test.mjs` pins the thresholds).
  2. **`fn_on_point_transaction()` no longer counts `adjust` rows as visits.** Voiding a transaction used to *increment* `visit_count` and push `last_visited_at` forward — i.e. cancelling a mistaken earn made the customer look *more* active. Visits/last-visit now count `earn`+`redeem` only; the points balance still sums every row (a void must move points). Includes a one-time backfill that temporarily disables `tr_customers_guard_points` (that guard blocks points writes at `pg_trigger_depth() = 0`, which is where a migration runs).
  3. **`get_loyalty_segment_counts()`** — returns total members, points outstanding, and per-segment counts computed **live** in SQL. `/loyalty/analytics` used to pull every `customers` row into Node to count them (slow as the base grows, and silently truncated if the project sets `db-max-rows`) *and* read the stale `rfm_segment` column. **The stale column was the real bug: the trigger only fires when a transaction arrives, but a lapsing customer is by definition one with no transactions — so nobody ever became `At-Risk`/`Lost`.** The app now computes segments live everywhere (`lib/rfm.js` for the single-customer badge, this RPC for the dashboard); the stored column is advisory only.
  4. **`uidx_point_tx_earn_receipt`** — unique partial index on `(branch_id, lower(trim(receipt_number))) where transaction_type = 'earn'`. The receipt number was mandatory but never checked, so one bill could be used to earn points repeatedly (the rate limiter only catches ≥5 earns to the *same* customer in 10 min). `issuePointsAction` pre-checks it for a readable message (which bill, when, to whom) and logs `FRAUD_ALERT_DUPLICATE_RECEIPT`; the index is the real guard and its `23505` is handled too. **If duplicates already exist the file skips creating the index and raises a NOTICE with the count** rather than failing — void the duplicates, then re-run.
  5. **`loyalty_redeem_reward(customer, reward, branch)`** — `SECURITY DEFINER`, does the points row + `redemption_history` + audit in one transaction with `select … for update` on the customer. Previously these were separate inserts: if the second failed, points were gone with no redemption record.
- **`sql/add_loyalty_rewards.sql` — catalog รางวัลใน DB** (idempotent). Run after `fn_my_role` exists; safe before/after `harden_loyalty_reads` (both define `fn_can_loyalty_staff`).
- **`sql/add_customer_privacy_consent.sql` — คอลัมน์ PDPA** บน `customers` (`privacy_consent_at` / `privacy_consent_version`).
- **`sql/optimize_queries.sql` — recommended for reports & analytics speed (2026-08-27)** (idempotent). Re-engineers `get_monthly_summary` using UNION ALL index scans + composite date/key indexes, reducing multi-second delays on heavy months (June/July) to milliseconds.
- **`sql/add_audit_forensics.sql` — run after `add_audit_context.sql`** (idempotent). Adds 12 columns to `audit_log` for tracing who changed data: `session_id` + `actor_email` (from `auth.jwt()`, unspoofable), `cf_ray` (correlates with Cloudflare's own logs), `forwarded_for` (the full proxy chain, vs the single chosen `ip_address` — shows a VPN/proxy in between), `referer`, `accept_language`, `http_method`, `browser` / `os` / `device_form` split out of `device_summary` so they can be filtered and grouped, plus `asn` / `city` (these two stay null unless Cloudflare Managed Transforms are enabled — that's expected, not a bug). Also creates `v_audit_session_anomaly`. **Re-run this file if you ever re-run `harden_security.sql` or `add_audit_context.sql`** — both ship older `fn_audit_log` / `fn_audit_log_config` that would overwrite these columns with nulls. `/admin/audit` degrades in tiers if it isn't applied (full → context-only → who/what/when) and names the missing file.
- **`sql/cleanup_legacy_tables.sql` — drops `employees`, `payroll_monthly`, `price_list`** (idempotent). Three tables created during the GAS port that the app never used: employee details live in `business_config.emp_details`, payroll is computed live by `lib/payslip.js` with history in `business_config.emp_pay_history`, and prices come from the catalog `expense-form` builds out of `expenses`. Verified 2026-09-09 — zero references anywhere in `app/`, `lib/`, `components/`, `templates/` or any other SQL file, and zero rows in production. Two reasons to actually drop them rather than leave them: **`price_list`'s read policy was `for select using (true)` with no `to authenticated`, so it applied to `PUBLIC` including `anon`** — anyone holding the publishable key (which ships in the browser bundle by design) could read it without an account, harmless only because it was empty; and `payroll_monthly` let any authenticated user INSERT/UPDATE. The file **refuses to drop anything if any of the three has rows** (raises a NOTICE instead) and deliberately avoids `cascade`, so an unexpected dependency errors loudly rather than being deleted along with it. It tightens the `price_list` policy first, so the hole closes even when the drop is skipped. `sql/supabase_migration.sql` still contains the original definitions — that file is never edited by convention, only annotated.
- **`sql/maintenance_audit_log.sql` — audit retention.** Creates `cleanup_old_audit_logs(p_days_to_keep int default 365)`, `SECURITY DEFINER`, admin-only, hard floor of 90 days so a typo can't wipe the trail. Driven from the **"ล้างบันทึกเก่า" card at the bottom of `/admin/audit`** (`app/admin/audit/actions.js` + `audit-purge.js`, double `window.confirm`, retention choices in `lib/audit-policy.js`). **Fixed three things on 2026-09-09 that made the file unrunnable** — nobody had noticed because nothing ever called it: it logged its own run via `write_audit_event('DELETE', …)`, but that function *rejects* `DELETE` (`raise 'invalid audit action'`) **and** the arguments were in the wrong order (a `jsonb` passed into the `text` `p_outcome` slot), so any call failed outright; it had **no `grant execute`**, so PostgREST couldn't reach it at all; and the `SECURITY DEFINER` body had no `set search_path`. It now inserts its own audit row directly instead of depending on `write_audit_event`'s signature — a purge always leaves a trace, otherwise clearing the log becomes the way to erase your tracks.
- **`sql/add_analytics_range_kpis.sql` — recommended for `/analytics` speed** (idempotent). Adds `get_months_kpis(p_month_labels)` so the page makes one RPC instead of N× `get_monthly_summary`; app falls back to the old path if not applied yet.
- `sql/add_free_cup_actual_cost.sql` — needed only for the free-cup evidence upload above; everything else in the core app works against the schema already in `sql/supabase_migration.sql`.
- **`sql/harden_security.sql` — security fix, recommend running regardless of which features you use.** See "Security model" above.
- **`sql/fix_bugs.sql` — run this one too, confirmed necessary in production (2026-07-28).** Fixes 3 things together: (1) `expenses` delete policy was admin-only in the original migration, widened to admin/co-admin/manager — without this, co-admin gets a silent-looking "ลบไม่สำเร็จ — ต้องมีสิทธิ์ admin หรือ manager" trying to delete a duplicate expense row; (2) `upsert_opex_item` wasn't setting `month_label` on insert, and the old `get_monthly_summary` filtered *all* expenses (including regular mat/bak/misc, which always had `month_label` set correctly via the `tr_expenses_month_label` trigger) by that same `month_label` string — so OPEX rows silently vanished from monthly reports; (3) backfills `month_label` on any pre-existing OPEX rows that were missing it. **Real incident this caused:** July 2026's "รายจ่ายรวม" showed 220,000+ ฿, staff's own manual count of just the material-cost category said ~70,000 ฿ — looked like duplicate/bad data entry, but `dedupMonthAction` found zero duplicates and a direct SQL sum of `ต้นทุนวัตถุดิบ` confirmed the material figure was already correct (81,926.50 ฿, matching staff's count within normal estimation slack). The inflated *total* was purely `get_monthly_summary` mis-handling OPEX under the hood — running `fix_bugs.sql` dropped the reported total from 220,000+ to 165,503.68 ฿, which now reconciles exactly against the sum of all 4 category rows in `/reports`. `sql/fix_opex_upsert.sql` is an earlier, narrower predecessor of just the `upsert_opex_item` ON CONFLICT fix — `fix_bugs.sql`'s version of that function supersedes it, no need to run both.

- **`sql/add_documents.sql` — required for `/admin/documents`** (idempotent; run after `harden_security.sql` and `add_audit_forensics.sql`). Creates table `documents` (metadata), the **private** Storage bucket `documents` (10 MB, images + PDF only), RLS on both `public.documents` and `storage.objects` limited to `admin` / `co-admin`, and audit trigger `tr_audit_documents`. `check_migrations.sql` column `add_documents` is true only when the table exists **and** the bucket is non-public. Until it is run, the page shows a hint naming this file.
- **`sql/new_instance_finalize.sql` + `scripts/install-schema.sh` — new shops only (2026-10-13), not a migration for a running shop.** `install-schema.sh` builds a blank Supabase project from the `sql/` files alone, so a new shop never connects to another shop's database (mamasaidno lives in a separate Supabase account). Its `FILES=( … )` array is **the** from-scratch order: base → `add_unit_column` → `add_email_to_profiles` → `admin_user_functions` → `harden_security` → `add_audit_context` → loyalty chain ending in `harden_loyalty_integrity` → `add_analytics_range_kpis` → `fix_bugs` → `optimize_queries` → `add_audit_forensics` → `add_free_cup_actual_cost` → `add_documents` → `maintenance_audit_log` → `cleanup_legacy_tables` → `new_instance_finalize`. Dry-run on an empty Postgres with Supabase stubs on 2026-10-13: every file passes and `check_migrations.sql` is all true; not yet run on a real Supabase project. **A new SQL file must be added to that array** (before `new_instance_finalize.sql`). The script refuses a target that already has app tables. The earlier runbook idea — schema-only `pg_dump` from the original shop, then re-running `add_loyalty_system.sql` for its seeds — was dropped: `pg_dump --schema=public` emits `CREATE SCHEMA public`, which aborts under `ON_ERROR_STOP`, and re-running `add_loyalty_system.sql` after the chain silently restores the pre-integrity `fn_on_point_transaction` (voids counted as visits).
- **`signup_trigger_removed` in `check_migrations.sql` (2026-10-13).** `sql/supabase_migration.sql` creates `on_auth_user_created` on `auth.users`, which copies `role` from `raw_user_meta_data` — data the person signing up supplies. With public signup enabled, `auth.signUp({ options: { data: { role: 'admin' } } })` yields an admin profile. Nothing in the app needs the trigger (`admin_create_user()` writes `profiles` itself). `new_instance_finalize.sql` part 1 drops it; on an existing shop where the column is `false`, run only that `drop trigger` line. Separately, **"Allow new users to sign up" must be off in Supabase Auth for every shop**: the base policies on `sales_daily` / `expenses` / `business_config` / `profiles` are `auth.role() = 'authenticated'`, so a self-registered account with no profile can still read them.

## Core access + receipt attachments (2026-10-22)

Run **sql/harden_sales_staff.sql** after harden_security.sql, add_free_cup_actual_cost.sql, optimize_queries.sql and any later file replacing report/OPEX RPCs. Atomic/idempotent: adds fn_page_cap, current-day Staff sales trigger, page-boundary policies and guarded existing RPC definitions without downgrading their installed bodies. Re-run it LAST if a legacy RPC migration is re-applied. check_migrations.harden_sales_staff verifies both trigger and all three RPC entry markers. It does not configure role_perms or create users.

Apply each to every shop database before deploying the corresponding features; only configure the requested shop's Staff matrix/account.
